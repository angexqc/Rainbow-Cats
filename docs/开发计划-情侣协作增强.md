# Rainbow Cats 情侣协作增强开发计划

## 1. 计划目标

以 `docs/情侣协作增强需求文档.md` 为唯一新增需求依据，在保持现有小程序和 Node API 主链路稳定的前提下，分阶段实现情侣共同决策、订单协作、偏好管理和用餐计划能力。

计划原则：先修复契约和数据安全，再实现共同选菜主流程，最后补充个性化和情绪价值功能。

## 2. 当前基线

### 已具备

- 微信登录、JWT 会话和资料维护。
- 配对码生成、绑定、解绑和有效期校验。
- 菜单、分类、购物车、随机点餐。
- 订单创建、幂等、状态流转、时间线和双方独立反馈。
- 订阅通知、图片上传和管理员权限基础。

### 当前验证限制

- 前端测试可在 `miniprogram/` 直接运行。
- Node API 测试依赖可写的 MySQL 测试库，当前环境若未提供 `rainbow_cats_test` 连接则无法执行完整后端门禁。
- 微信开发者工具中的真机交互和订阅消息需要人工验收。

## 3. 优先级总览

| 优先级 | 阶段 | 目标 | 交付结果 |
| --- | --- | --- | --- |
| P0 | 0 | 契约与权限收口 | 前后端字段、权限、并发和错误行为一致 |
| P0 | 1 | 共同选菜 MVP | 两个人能独立表达意愿并得到共同菜单 |
| P0 | 2 | 订单协作闭环 | 共同菜单稳定进入订单并完成确认 |
| P1 | 3 | 同步与通知 | 轮询、站内状态和订阅消息形成兜底 |
| P1 | 4 | 偏好、忌口、收藏 | 推荐更符合双方真实习惯 |
| P2 | 5 | 用餐计划与情侣记录 | 建立持续使用和纪念场景 |

## 4. 阶段 0：契约与权限收口（P0）

### 目标

先消除现有实现与需求之间的权限、字段和失败处理差异，为后续新增领域提供稳定基础。

### 后端任务

- 固化用户、配对、菜单、订单、反馈、通知和上传表的字段契约。
- 补齐菜单查看/创建/编辑/上下架/删除权限矩阵测试。
- 补齐订单创建者、配对方、第三方的查看和状态操作矩阵测试。
- 确认订单 `idempotency_key + creator_user_id` 唯一约束和冲突响应。
- 确认订单状态使用 `version` 条件更新，冲突返回领域错误。
- 确认配对码 `active/used/expired/revoked` 生命周期和事务消费。
- 确认通知模板只有管理员可修改，普通用户只能修改自己的通知开关。

### 前端任务

- 统一处理 `12001/12002/12003/13002/13003/13004/14005/14006`。
- 确认页只提交 `menuId/count/remark/idempotencyKey`，不信任客户端菜品快照。
- 菜单列表保留后端返回的完整字段，并按当前查看者派生 `me/ta`。
- 配对页展示有效期和错误状态。
- 通知授权失败、模板缺失和网络异常不得阻断下单。

### 验证门禁

- 前端 `npm test`。
- 后端认证、授权、订单、配对、上传测试。
- A/B/C 三用户访问矩阵：本人、伴侣、第三人、解绑后。
- 静态契约检查：字段名、错误码、请求路径和响应结构。

### 依赖与风险

- 依赖后端测试数据库；无测试库时只能完成语法和静态检查。
- 不在此阶段引入新业务表，避免契约未稳定就扩展数据模型。

## 5. 阶段 1：共同选菜 MVP（P0）

### 目标

实现情侣共同决定吃什么的最小闭环，不依赖 WebSocket 或支付能力。

### 数据库

新增：

- `candidate_items`
- `candidate_votes`

约束：

- `scope_key + menu_id` 唯一，避免同一作用域重复候选。
- `candidate_id + actor_user_id` 唯一，双方选择互不覆盖。
- 候选项只能属于当前用户或当前配对作用域。

### 后端接口

- `GET /api/candidates`
- `POST /api/candidates`
- `PATCH /api/candidates/:id`
- `DELETE /api/candidates/:id`
- `POST /api/candidates/:id/vote`
- `GET /api/candidates/summary`

后端负责：

- 校验菜单仍在双方可见范围内。
- 校验候选菜是否下架或删除。
- 根据双方 `want/neutral/avoid` 计算共同结果。
- 返回相对角色，不直接保存 `me/ta`。

### 前端页面

- 菜单页增加“加入候选”和候选数量入口。
- 新增候选清单页，展示双方头像、选择状态和共同结果。
- 菜品详情增加加入候选和意愿表达。
- 首页展示候选摘要和“查看共同选择”入口。
- 共同结果支持一键加入购物车，不直接创建订单。

### 验收标准

- A、B 可以分别对同一道菜表达选择，互不覆盖。
- `want + want` 优先级最高。
- 任一方 `avoid` 的菜不进入共同推荐。
- 解除配对后不能继续读取原配对候选。
- 重复点击和重复请求不会生成重复候选或重复选择。

## 6. 阶段 2：订单协作闭环（P0）

### 目标

将共同选择稳定转入现有购物车和订单流程，并清晰呈现双方操作。

### 后端任务

- 订单创建继续由后端重建菜品快照。
- 订单查询返回 `creatorUserId`、`timeline.actorUserId` 和 `feedbackList`。
- 校验创建者只能取消，配对方只能确认/完成。
- 完成订单后允许双方分别写入反馈。
- 对下架、删除、配对解除和并发状态更新返回明确领域错误。

### 前端任务

- 候选结果批量加入购物车。
- 购物车区分候选转入的菜品和普通加入的菜品，但不改变下单数据结构。
- 确认页展示双方头像、订单发起人和备注。
- 订单历史和详情统一显示相对角色和时间线操作人。
- 失败后保留 checkout 和未提交购物车，仅成功后清理已提交项。

### 验收标准

- 共同菜单可进入确认页并成功下单。
- 重复点击确认不会重复创建订单。
- 菜品下架时订单创建失败，购物车保持可恢复。
- 同一订单并发确认/完成只有一个请求成功。
- 双方评价内容独立保存，互不覆盖。

## 7. 阶段 3：同步与通知（P1）

### 目标

在个人开发者可维护的前提下，让双方及时看到候选和订单变化。

### 后端任务

- 候选和订单接口返回 `updatedAt` 或等价最后更新时间。
- 完善 `notification_deliveries` 事件幂等、有限重试和失败记录。
- 支持配对成功、订单确认、完成、取消等通知事件。

### 前端任务

- 页面进入时刷新候选、订单和配对状态。
- 页面停留时按 15～30 秒轮询，离开页面停止轮询。
- 增加站内红点、待处理状态和最后同步时间。
- 订阅消息拒绝、模板缺失时显示站内替代状态。

### 验收标准

- 轮询不会重复创建请求或造成页面状态闪烁。
- 页面隐藏后停止定时器，重新进入后恢复同步。
- 订阅消息失败不影响订单主流程。
- 相同事件不会重复写入通知投递记录。

## 8. 阶段 4：偏好、忌口、收藏（P1）

### 数据库

新增：

- `user_food_preferences`
- `menu_user_marks`

### 后端接口

- `GET/PATCH /api/preferences`
- `GET/POST/DELETE /api/favorites`
- `GET/POST/DELETE /api/wish-list`

### 前端页面

- 我的页面增加偏好和忌口入口。
- 菜单卡片增加收藏、想吃操作。
- 首页和随机点餐按用户偏好过滤。
- 下单前提示可能的忌口/过敏冲突。

### 验收标准

- 偏好默认仅本人可见，开启共享后伴侣可见。
- 收藏、想吃、候选、购物车状态互不混淆。
- 随机点餐不会推荐明确排除的菜品。
- 删除菜品后历史收藏不造成页面崩溃。

## 9. 阶段 5：用餐计划与情侣记录（P2）

### 数据库

新增：

- `meal_plans`

### 功能

- 创建午餐/晚餐计划。
- 双方查看、编辑和确认计划。
- 计划到期转为历史记录，不自动创建订单。
- 完成订单后生成轻量“今日一起吃饭”记录。
- 展示本周共同完成订单次数和常点菜品。

### 验收标准

- 计划按配对作用域隔离。
- 解绑后旧计划按产品定义处理，不被新关系错误继承。
- 计划不会绕过确认页直接创建订单。
- 记录数据缺失时有空状态，不展示伪造统计。

## 10. 迭代顺序与里程碑

| 里程碑 | 完成条件 |
| --- | --- |
| M0 契约稳定 | 阶段 0 测试和静态门禁通过 |
| M1 共同选择可用 | 候选、投票、共同结果接口和页面可用 |
| M2 订单闭环 | 共同结果可下单，幂等和并发验证通过 |
| M3 协作可感知 | 轮询、站内状态、订阅消息兜底完成 |
| M4 个性化可用 | 偏好、忌口、收藏和想吃清单完成 |
| M5 关系沉淀 | 用餐计划和情侣记录完成 |

每个里程碑必须同时满足：代码实现、接口契约、数据库迁移、自动化测试、人工验收记录和失败回滚说明。

## 10. 后续扩展设计

本阶段不实现所有扩展能力，但必须为后续演进保留稳定边界。

### 10.1 数据模型演进

- 所有新表使用独立迁移脚本，迁移具备版本号、执行记录和可重复执行能力。
- 业务表保留 `created_at/updated_at`，需要软删除的对象增加 `deleted_at` 或状态字段，不直接物理删除关键历史。
- 关系数据统一使用 `scope_key` 表示单人或情侣作用域；未来扩展家庭、多人菜单时，将作用域抽象为独立 `spaces`/`members` 模型，不修改现有订单历史语义。
- 菜品、订单和计划通过稳定 ID 关联；展示字段只能作为快照，不能作为关联键。
- 枚举字段允许向前兼容：服务端新增状态时，旧客户端按未知状态兜底，不因反序列化失败崩溃。

### 10.2 接口与客户端扩展

- 新接口先以 `/api` 下独立资源发布；发生破坏性变更时使用 `/api/v2`，不覆盖旧字段含义。
- 列表接口统一返回分页结构，并允许未来增加 `cursor` 分页而不删除 `page/pageSize`。
- 响应保留 `requestId`、`updatedAt` 和领域错误码，便于问题追踪、增量同步和客户端重试。
- 前端新增领域服务时继续采用“页面 -> apiStore -> services -> http”链路；不在页面内直接拼接接口。
- 复杂功能通过功能开关控制，支持按用户、配对关系或版本灰度启用。

### 10.3 事件与通知扩展

- 候选、订单、计划等领域动作预留事件名，例如 `candidate.updated`、`order.status_changed`、`meal_plan.reminded`。
- 通知发送继续通过 `notification_deliveries` 记录事件键、接收人和重试状态；未来可增加站内通知而不改变业务写接口。
- 事件生产与业务事务使用 outbox 或等价可靠记录，避免“数据库成功、通知丢失”。
- 订阅消息、站内红点和未来模板消息都消费同一事件，不在页面中复制业务判断。

### 10.4 推荐与规则扩展

- 将“共同菜单计算”抽象为可测试的规则服务，当前使用 `want/neutral/avoid`，未来可加入口味、历史、时间和库存规则。
- 推荐结果返回原因和规则版本，例如 `resultReason`、`ruleVersion`，方便解释和回溯。
- 不在第一阶段引入机器学习依赖；先积累明确授权的偏好和行为数据。

### 10.5 多端与数据导出

- 后端不依赖微信页面生命周期，未来可复用到 H5、桌面端或管理后台。
- 身份层保留 `userId` 与微信身份映射，未来可增加其他登录方式而不改变业务表主键。
- 预留用户数据导出和关系解除后的数据处理策略；历史订单、反馈和审计记录不可因解绑直接丢失。

### 10.6 扩展门禁

任何后续功能进入开发前，必须回答：

1. 是否属于现有用户/情侣作用域，还是需要新的空间模型？
2. 是否需要新的绝对操作人字段、审计记录和幂等键？
3. 是否会改变现有订单、配对或通知状态机？
4. 是否能在微信个人开发者能力范围内降级运行？
5. 是否有独立迁移、接口契约、权限矩阵和回滚方案？

## 11. 回滚与风险控制

- 新增表采用独立迁移，不修改旧表语义；回滚时先停用入口，再回滚代码和迁移。
- 新增接口保持独立路由，旧页面继续可用。
- 候选和偏好功能使用功能开关或入口隐藏控制发布范围。
- 不删除历史订单、时间线、反馈和上传文件记录。
- 任何写入失败都不得回退为 mock 成功。
- 发现数据作用域、权限或角色派生不一致时，停止当前阶段发布，先修复契约。

## 12. 最终发布门禁

- 前端 `cd miniprogram && npm test` 通过。
- 后端使用独立测试库运行 `npm test` 和 test gate。
- 完成 A/B/C 用户授权矩阵。
- 完成配对、解绑、换绑、候选、购物车、订单幂等、并发、通知和上传验收。
- 微信开发者工具完成 iOS/Android 主要页面检查。
- 需求文档、字段映射、架构图、测试用例和验证日志保持一致。
